The Transfer API handles all physical stock movements between locations in your retail network — whether that is a distribution centre pushing goods to a store, a store pulling from the DC, a store-to-store transfer, or a return shipment back to the DC. Combine import and export endpoints to drive the full transfer lifecycle from initiation through receipt confirmation.

## Import Endpoint

**POST /import/transfers** — Create or update a transfer record in Tilroy.

Use this endpoint to tell Tilroy about a stock movement. Depending on the flags you include, a single import message can initiate a transfer, confirm receipt, close an open request, or trigger automatic dispatch for a home-delivery order. All import calls are asynchronous: Tilroy validates on receipt, returns `202 OK`, and processes the message in a background queue.

See the [Transfer API reference](https://tilroy-apidocs-prd.s3.eu-west-1.amazonaws.com/transferapi.html) for the full request schema.

## Export Endpoint

**GET /export/transfers** — Retrieve transfer events generated by Tilroy.

Tilroy publishes transfer events whenever a transfer is initiated, received, or results in a difference. Poll this endpoint to reconcile your DC or ERP system with what stores have actually received. Use the `idSource` field to correlate export events back to the import messages your system originally sent.

## Key Parameters

| Parameter | Type | Description |
|---|---|---|
| `idSource` | string | Your own reference ID for this transfer. Use it to correlate import messages with the corresponding export receipt events. |
| `isRequest` | boolean | Mark this transfer as a pull request from a store to the DC. Sets status to `Q` (queued/requested). |
| `doReceipt` | boolean | Automatically mark the shipment as received at the destination when the transfer is processed. |
| `doCloseRequest` | boolean | Close an open transfer request once the shipment has been dispatched. |
| `doCheckOffOpenRequests` | boolean | Automatically match this transfer against open store requests, fulfilling them where possible. |
| `doDispatch` | boolean | Automatically dispatch a home-delivery order when the transfer is processed. |
| `quantityTransferred` | integer | The number of units sent from the source location. |
| `quantityReceived` | integer | The number of units confirmed received at the destination. |
| `basedOn` | string | Reference to the original transfer record. Used when creating a difference transfer for a quantity discrepancy. |

## Transfer Statuses

| Status | Description |
|---|---|
| **Q** | Transfer request queued — a store has requested stock from the DC but it has not yet been dispatched. |
| **T** | In transit — stock has been dispatched from the source but not yet confirmed received at the destination. |
| *(received)* | Receipt confirmed — `quantityReceived` has been set and the transfer is complete. |

<Note>
  Always include `idSource` when importing transfers. Tilroy includes this value in the corresponding export event, so you can match receipts back to the original shipment record in your ERP or warehouse system without ambiguity.
</Note>

## Transfer Flows

<Tabs>
  <Tab title="DC → Store (Push)">
    Use this flow when your DC proactively pushes stock to stores.

    <Steps>
      <Step title="Import the transfer">
        POST to `/import/transfers` with the source (DC) and destination (store), quantity, and your `idSource`. Set status to `T`.
      </Step>
      <Step title="Store receives">
        Tilroy publishes a transfer export event. The store confirms receipt, updating `quantityReceived`.
      </Step>
      <Step title="Handle differences">
        If `quantityReceived` differs from `quantityTransferred`, Tilroy automatically creates a reverse difference transfer for the delta. Use `basedOn` to link the difference transfer to the original.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Store → DC (Pull)">
    Use this flow when a store requests stock from the DC.

    <Steps>
      <Step title="Store creates a request">
        POST to `/import/transfers` with `isRequest: true` and status `Q`. The store specifies the SKU and quantity needed.
      </Step>
      <Step title="DC fulfils the request">
        POST a new transfer referencing the original request's Tilroy ID. Use `doCloseRequest: true` to close the open request.
      </Step>
      <Step title="Store receives">
        Tilroy publishes the receipt event. Reconcile using `idSource`.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Store → Store">
    Store-to-store transfers follow the same pull flow. The requesting store creates a transfer request (`isRequest: true`), and the source store sends a fulfilment transfer referencing the request.
  </Tab>
  <Tab title="Return to DC">
    Use this flow when a store returns stock to the DC.

    <Steps>
      <Step title="Store initiates the return">
        POST to `/import/transfers` with the store as source and DC as destination, status `T`.
      </Step>
      <Step title="DC confirms receipt">
        POST a confirmation import with `quantityReceived` set to the actual quantity received.
      </Step>
    </Steps>
  </Tab>
</Tabs>
